## Implementation and supported versions

- Both Android workflows generate the Capacitor project and call `scripts/android/prepare.mjs bridge`. The tracked `android-native/health-connect-activities.xml` supplies activities/aliases; the installer adds the six read permissions, provider visibility, native source and native tests. Do not manually patch generated `android/`.
- App identity remains `com.nextleveldigitalmedia.phatbot`, PHATBOT, `https://app.phatbotfit.com`; minimum SDK 26, Capacitor 8.5.0, Health Connect 1.1.0. No dependency upgrades, write, background, extended-history, medical, location or route permissions.
- API 26–27: PHATBOT still runs; Health Connect is unavailable. No installation loop or permission prompt.
- API 28–33: SDK availability is checked; the provider package is visible through `<queries>`. An explicit install/update action opens the Health Connect Play listing when the SDK reports an absent/outdated provider. Unavailable profiles/devices remain unavailable.
- API 34+: uses the system Health Connect module. `VIEW_PERMISSION_USAGE` and `HEALTH_PERMISSIONS` resolve to an exported alias protected by `START_VIEW_PERMISSION_USAGE`, targeting the privacy activity. Settings open using the SDK action; no APK-install suggestion for this version range.
- The pre-14 rationale intent targets the same privacy activity. It displays the existing public policy in an isolated, JavaScript-disabled WebView (no Capacitor bridge), with browser fallback and a native explanation. It ignores intent URLs and never reads health data.
- Current Android guidance also requires onboarding entry points when permission approval alone is insufficient. PHATBOT needs account sign-in and a disclosure acknowledgement, so protected pre-14/platform onboarding components explain how to open Me > Health & Wearables. They never prompt automatically.

The implementation follows the [current integration guide](https://developer.android.com/health-and-fitness/health-connect/get-started) and [availability guidance](https://developer.android.com/health-and-fitness/health-connect/availability). The guide currently shows a newer alpha dependency; none of these requirements requires replacing PHATBOT's stable 1.1.0 dependency. API 26 is the library minimum, not the minimum usable Health Connect provider version.

## Permission-to-feature audit

All retained categories are read locally and transmitted/stored when a signed-in athlete explicitly syncs and the category has readable data. Missing/denied values are omitted, not invented. The nine original permissions were traced through the native bridge, `src/lib/healthconnect.ts`, `src/lib/health.ts`, `src/lib/healthSync.ts`, cardio/recovery views and schema.

| Permission | Actual PHATBOT use and stored fields | Decision |
| --- | --- | --- |
| `READ_STEPS` | Daily aggregate → `health_daily_metrics.steps`; Activity daily steps and existing competition step calculations. | Retain |
| `READ_ACTIVE_CALORIES_BURNED` | Daily aggregate → `health_daily_metrics.active_energy_kcal`; per-exercise aggregate → `cardio_activities.active_energy_kcal`, shown as Active energy in the completed cardio report. | Retain |
| `READ_EXERCISE` | Session identity, type, start/end and duration → `cardio_activities`; activity history, whole-workout dashboard/report and existing activity calculations. | Retain |
| `READ_DISTANCE` | Distance aggregate within each approved exercise interval → `cardio_activities.distance_meters`; workout distance, pace/speed, volume and milestones. Requires exercise access for an associated workout. | Retain |
| `READ_HEART_RATE` | Mean HR within each approved exercise interval → `cardio_activities.average_heart_rate_bpm`; completed cardio report. Raw HR samples are not sent. Requires exercise access for an associated workout. | Retain |
| `READ_SLEEP` | Sleep session start/end/duration → canonical `health_sleep_nights` intervals/quality flags when that existing table is available; Sleep & Recovery displays the session-only limitation. Android session spans are **not** treated as actual asleep duration or reliable sleep/performance evidence. | Retain; normalization unchanged |
| `READ_RESTING_HEART_RATE` | Previously read the newest value and stored it on the sync date in `health_daily_metrics.resting_heart_rate_bpm`. No Android-facing consumer was found; the recovery status component using it is iOS-only. | Remove Android request/read, explicitly approved by Eric |
| `READ_HEART_RATE_VARIABILITY` | Previously read newest RMSSD and stored it on the sync date in `health_daily_metrics.hrv_ms`. No Android-facing consumer was found. | Remove Android request/read, explicitly approved by Eric |
| `READ_WEIGHT` | Previously returned latest `weightKg` to JavaScript but nothing saved/displayed it. The weight chart uses manually logged bodyweight measurements. | Remove Android request/read, explicitly approved by Eric |

Historical values, database columns and iOS imports remain unchanged. Old Android APKs can still request their old permission set until updated; removing manifest requests does not erase Health Connect provider records or saved PHATBOT history. No new health functionality is implied by retaining optional fields in shared TypeScript snapshot types for compatibility.

## Actual data flow and controls

`Health Connect → HealthConnectPlugin → Capacitor JS bridge → health.ts → authenticated healthSync.ts → Supabase canonical tables → athlete views/reports and existing competition refresh RPC`.

- Local source data is read in the foreground, normally for 14 days. Requested windows are bounded to 1–14 days; daily aggregates retain the existing local-calendar-day behavior. No background scheduler or history-access permission is added.
- Before the first read in this updated native build, the athlete explicitly acknowledges a native explanation of categories, read-only access, off-device transmission and Supabase/account storage. The web card repeats that explanation and links the same policy. Declining does not affect normal PHATBOT use. The acknowledgement is stored locally on this installation; Android grants remain authoritative and are checked before every snapshot.
- The old implementation launched Android's permission screen and immediately returned `authorized: false`, then required every permission to read anything. The bridge now waits for the activity result and re-queries grants. Partial grants are usable. Each optional read is permission-gated; a failed/revoked category yields unknown plus a sanitized warning while other approved categories can succeed. No automatic permission retries.
- Me shows current native access rather than treating a historical database sync row as permission state. Access is refreshed on native resume, visibility/focus, explicit refresh and after actions. Settings/install actions are user-initiated. Repeated taps are guarded. Missing bridge methods in older APKs show an update/retry explanation instead of claiming access.
- The existing authenticated sync validates the user again after the native read, preserves stable workout IDs (`source_workout_id`) with `source=health_connect`, and upserts by existing keys. Missing quantities preserve known saved data. There is no duplicate ingestion path or new backend implementation.
- Exercise/sleep record pages are exhausted rather than silently truncating the provider response. Sleep values keep the existing session-only representation; no sleep-stage feature is added. Distance samples/standardized segments are **not** synthesized by Android. The existing segment engine runs only when genuine samples exist.
- Daily steps/calories, session IDs/times/types/durations and available workout distance/calories/average HR leave the device and persist; they are not merely ephemeral processing. Sleep intervals, source, timezone/window, quality flags and method version are stored by the existing sleep pipeline when available. No new raw HR time series, weight, RHR or HRV leaves this updated Android bridge. Permissions/status and read warnings are transient UI state; the successful sync timestamp is stored in `athlete_health_connections`.
- Existing competition refresh remains in place. Rules and scoring are unchanged; imported steps/activity can affect existing standings. Do not describe all imported data as private-only without considering existing athlete/coach/competition access and the user's choices.

No production database queries or mutations were needed for this code/schema audit. Production table availability, service-provider retention, actual access policies/configuration and end-to-end deletion need owner verification; repository evidence is not a certification of the deployed environment.
